# 결정 기록

사용자가 정한 것을 문서에 적는 하나뿐인 절차다. 선택 UI, 대화, 웹 대화, 비교판 중 어디서 정했든 이대로 적는다.
- **확정**은 사용자가 직접 고른 것뿐이다. Claude의 생각은 **제안**, 아직 안 정한 것은 미정 항목이다 (CLAUDE.md "사용자와 일하는 방식").
- 결정은 메모리가 아니라 저장소 문서에 적는다. 메모리는 컴퓨터마다 따로다.
- 이 절차는 문서만 고친다. 코드·데이터·씬·테스트는 바뀔 곳을 적어 두고 지금 할지 묻는다 (3).

## 부르는 법

- `/decide <정한 것>`으로 부르면 뒤의 말이 결정이다. 대화에서 방금 정했으면 그 말이나 선택 UI의 답이 결정이다.
- 다른 스킬·서브에이전트는 아래 세 줄을 넘긴다. 날짜를 모르면 오늘이다 (`date +%F`).

```
결정: <사용자의 말 그대로>
출처: <선택 UI의 질문과 고른 답 / 대화 / 붙여 넣은 글 / 비교판>
날짜: <YYYY-MM-DD>
```

- 서브에이전트 안에서는 선택 UI를 쓸 수 없다. 이렇게 사용자에게 물을 수 없으면 문서를 고치지 않는다. 1~2에서 찾은 것과 3에서 물을 것을 5의 꼴로 돌려주면, 메인 대화가 묻고 이 절차로 적는다.

## 1. 정한 것 못 박기

- 사용자의 말을 그대로 옮겨 둔다. 범위(어느 몬스터, 어느 화면, 어느 값까지)도 사용자의 말에서만 읽는다.
- 여러 결정을 한꺼번에 받으면 하나씩 나눠 같은 절차를 밟는다.
- "제안대로", "그걸로"처럼 내용이 없는 결정은 가리키는 것을 찾는다 (대화, 붙여 넣은 글, 문서의 **제안** 줄). 못 찾으면 지어내지 않고 묻는다.
- 사용자가 말하지 않은 세부(따라 나오는 하위 규칙, 값, 범위)는 확정이 아니다.
  - 지금 구현하는 데 필요한 세부: 3에서 묻고, 답을 받기 전에는 **제안**으로 적는다 (CLAUDE.md).
  - 아직 구현하지 않는 기능이라 당장 필요 없는 세부: 미정 항목에 질문으로 더한다. 제안을 미리 쓰지 않는다.
- 사용자가 말한 이유는 짧게 같이 적는다. 이유를 지어내지 않는다.
- 다른 곳의 말은 문서의 말로 바꿔 적되 뜻은 그대로 둔다 (예: 설계 문서는 "얼굴뼈"를 "머리뼈"로 바꿨다).
- 의논 없이 바로 정한 결정에 뚜렷한 단점이 보이면 3에서 근거와 함께 한두 줄로 말한다 (CLAUDE.md). 선택 UI나 비교판에서 장단점을 보고 고른 결정은 다시 따지지 않는다.

## 2. 적을 곳과 어긋나는 곳 찾기

| 결정 | 적는 곳 |
|---|---|
| 게임 규칙·값 (몬스터, 언데드, 머리뼈, 조작, UI 동작) | `docs/game-design.md` |
| 그림·화면 (시점, 카메라, 팔레트, 크기, 앞벽) | `docs/art-direction.md` |
| 진행 중인 작업의 방식 (단계, 순서, 브랜치, 측정 기준) | 그 작업의 계획 문서(`docs/plans/`)의 "정한 것" 절 |
| 에셋 그림을 확정 | `make-asset` 스킬 "6. 기록" (`assets/ASSETS.md`의 상태) |
| 두 컴퓨터에서 늘 지킬 작업 규칙 | `CLAUDE.md` (짧게. 상황별 설명은 맞는 스킬에) |

- 계획 문서에서 정한 게임·그림 규칙은 확정 문서에도 적고 계획 문서를 가리킨다 (예: `docs/art-direction.md`의 "동굴 지형").
- 설계 문서는 미리 불러오지 않는다. 목차(`grep -n '^##' docs/game-design.md`)로 줄 번호를 찾아 그 절, "미정 항목" 절, "설계 검토 메모" 절을 읽는다.
- Grep 도구로 저장소 전체에서 결정의 낱말, 옛 값, 관련 말을 찾는다.
  - 숫자는 단위나 앞뒤 말과 함께 찾는다 (예: `350px`, "사거리").
  - 코드에서 나온 곳은 앞뒤 주석도 본다. 임시값을 확정하는 결정이면 찾은 코드 파일 안의 "임시"도 찾는다. 값 옆 주석에 남기 쉽다. 설계 문서는 임시값이 많아서 이렇게 찾지 않고 그 절을 읽는다.
  - `tests/balance/results/`의 측정 기록과 지난 커밋 메시지는 그때의 기록이라 고치지 않는다.
- 찾은 곳을 나눈다.
  - 적을 곳, 옛 값이 남은 곳 (다른 절, 표, 다른 문서, CLAUDE.md)
  - 닫을 미정 줄
  - 결정과 어긋나는 **확정** 줄
  - 결정과 바로 이어진 **제안** 줄 (같은 값, 같은 규칙. 같은 절의 다른 제안은 넣지 않는다)
  - 닿는 설계 검토 메모
  - 코드·데이터·씬·테스트(시나리오 맨 위 `##` 주석 포함): 고치지 않고 "구현에서 바뀔 것"으로 적는다
- 결정이 이미 문서에 그대로 있으면 고치지 않고 그렇다고 알린다.

## 3. 물을 것은 모아서 묻기

선택 UI로 한 번에 묻는다. 4개까지이고, 더 많으면 중요한 것부터 나눠 묻는다. 추천안을 첫 번째에 두고 선택지마다 장단점을 짧게 적는다.
- 확정 줄을 바꾸거나 지우는 것: 그 줄(파일:줄, 지금 문장 → 바꿀 문장)을 보여 주고 묻는다. 사용자가 그 줄을 직접 짚어 바꾸라고 했으면 묻지 않는다 (그때도 지운 예전 결정은 5에서 알린다). 고칠 곳이 사용자가 짚은 것보다 넓으면(다른 절, 다른 문서) 묻는다.
- 지금 구현에 필요한데 사용자가 말하지 않은 세부
- 결정과 바로 이어진 **제안**을 같이 확정할지
- 구현에서 바뀔 것이 있으면 지금 할지. 사용자가 처음부터 구현까지 하라고 했으면 묻지 않는다.
- 1에서 본 뚜렷한 단점

답이 없거나 "나중에"면 그 부분은 **제안**이나 미정으로 두고 나머지를 적는다.

## 4. 문서의 꼴대로 적기

날짜는 언제나 `YYYY-MM-DD`다. 아래는 `docs/game-design.md`의 꼴이다. 다른 문서는 그 문서에 이미 있는 꼴을 따른다.
`docs/art-direction.md`는 기본 방향 표의 상태 칸을 고치거나, "제안 (사용자 확인 전)" 절의 줄을 "확정된 규칙" 절로 옮긴다. 계획 문서는 "정한 것 (사용자, YYYY-MM-DD)" 절이나 `**확정** (사용자 결정, YYYY-MM-DD):` 줄로 적는다. 틀(`docs/plans/_template.md`)로 만든 계획이면 그 단계의 "사람이 정할 것"에 있던 줄을 아래 미정 항목처럼 닫는다.

- 확정 절(`## <주제> — 확정`)에 더하는 결정은 관련 줄 곁에 두고, 문장 끝에 `(사용자 결정, YYYY-MM-DD)`를 붙인다. 괄호에 예전 결정 날짜가 있으면 새 날짜로 바꾼다 (날짜는 마지막 결정 하나만). 고른 값만 적을 때는 `값 (사용자 확정): …`를 쓴다.
- 새 주제는 `## 미정 항목` 앞, 가까운 주제 옆에 `## <주제> — 확정 (YYYY-MM-DD)` 절로 만든다. 있는 절에 더할 때는 절 제목의 날짜를 그대로 둔다.
- 제안을 확정할 때: `**제안**:`이나 `**제안** (구현에는 이렇게 넣었다, 확인 필요):`를 떼고, 사용자가 고른 대로 고쳐 날짜를 붙인다. 제안 묶음에서는 고른 줄만 묶음 밖으로 옮긴다.
- 임시를 확정할 때: `(임시값)`, `**임시**:`, "나중에 정한다" 같은 말을 뗀다. 사용자가 "일단", "지금은"이라고 했으면 `임시값`을 남기고 날짜만 붙인다.
- **검토 중**은 결정이 아니다. 사용자가 정하면 표시를 떼고 위 꼴로 적는다.
- 값을 바꿀 때: 문장 속 값을 새 값으로 고치고 괄호에 짧은 내력을 붙인다. 예: `(사용자 결정, 2026-11-12. 250에서 올림. …)`. 여러 번 바뀌면 `120 → 160 → 300`처럼 잇는다.
- 규칙을 바꿀 때: 새 규칙을 적고 `(YYYY-MM-DD 바꿈. 처음에는 … 해서 …)`를 붙인다. 버린 안을 다시 꺼내지 않게 할 까닭이 있을 때만 `"<안>"(B)는 넣지 않는다 (사용자 결정, YYYY-MM-DD)`나 `메모: 예전에는 …`를 남긴다.
- 옛 값이 남은 곳을 같이 고친다. 예: 사거리를 160에서 300으로 바꿀 때 "네크로맨서의 공격 반경(기본 공격 사거리, 지금 160)"과 투사체 도착 시간 표도 고쳤다.
- 미정 항목:
  - 다 정한 줄은 지운다 (`[x]`로 남기지 않는다). `###` 묶음이 비면 묶음 제목도 지운다.
  - 일부만 정했으면 남은 것만 남게 고쳐 쓰고 정한 절을 가리킨다. 예: `- [ ] 수리 비용 (지금은 …, 임시. 위 "수리 기계")`
  - 결정 때문에 새로 생긴 질문은 맞는 묶음에 `- [ ]` 줄로 더한다. 확정 절에서는 남은 부분을 "…은 미정이다"나 `(미정)`으로 가리킨다.
- 설계 검토 메모는 판단 재료라 고치지 않는다.

## 5. 보고

- 문서를 고쳤으면 `bash tests/check_rules.sh`를 돌린다 (CLAUDE.md·스킬을 고쳤으면 꼭).
- 사용자에게 짧게 알린다. 한 줄에 하나씩:

```
정한 것: <사용자의 말> (<날짜>, <출처>)
고친 곳: <파일:줄> <전> → <후> (바뀐 부분만. 지운 예전 결정은 꼭 적는다)
제안·미정으로 남긴 것: <줄과 물은 것, 없으면 없음>
구현에서 바뀔 것 (아직 안 함): <파일:줄> <지금> → <바뀔 것>, 없으면 "없음"과 까닭
닿는 설계 검토 메모: <있을 때만>
확인: bash tests/check_rules.sh → <마지막 줄>
```

- 커밋과 push는 사용자가 하라고 한 것만 한다 (CLAUDE.md). 기록만 했으면 커밋할지 묻는다. 이어서 구현하면 그 작업이 끝날 때 함께 묻는다. 커밋 메시지는 결정 한 줄이면 된다 (예: "수리 비용 확정: 뼈 1개 = 내구도 1").
